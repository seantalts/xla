## Internal divergences and known regression history (calibration anchors)

The internal branch differs from the OSS branch in at least three ways; experiments must use the semantics of the branch under test, and the three incidents below are mandatory non-regression checks for ANY gating change:

1. **Module gate exists internally:** `max_instruction_count`, originally 2,000, now 5,000. Incident: inference_gym (3,011 instructions) fell over the 2,000 gate, disabling hoisting entirely, +37%; fixed by raising to 5,000 with >10,000 (Gemma-class) still excluded for compile-time protection.
2. **`min_region_size` = 3 counting only thunk-generating instructions** (OSS counts all members, min 4). Incident: diffrax (+633%) and jax.b380442861 (+1321%) from hoisting tiny copy-only regions whose kernel ABI cost exceeded any dispatch savings; fixed by the thunk-generating count.
3. **Loop-fusion availability is amplification-aware:** under `use_experimental_loop_fusion`, loop fusions (except kDot) are unavailable for hoisting to protect them for the new emitters. Incident: this made scan loops containing them un-hoistable, +550% on high-trip-count loops; fixed by treating such fusions as available in loop-amplified contexts. Consequence to keep in mind: fusions inside hoisted loops get legacy emission, trading new-emitter code quality for dispatch elimination; run gating experiments with this flag both on and off.

## The three questions to answer with data

1. **Module-size gate: it exists (internally, now 5,000) and has already mispredicted once in the predicted direction; determine whether to replace it.** The structural problem: much of the benchmark corpus is *partial-model* HLO (a slice of a larger program), so module-level thresholds calibrated on the suite do not transfer to production. The inference_gym incident is this failure observed live: a threshold that looked safe on the suite disabled hoisting on a 3,011-instruction model, and the fix (raise to 5,000) is a point patch; the next loop-dominated model at 6k regresses silently, and slice-benchmarks will not show it. Run-level criteria (byte budget, member cap, amplification, thunk-generating min size) are composition-invariant: a run behaves the same whether it sits in a 100-instruction slice or a 30k-instruction model. Known module counts for orientation (total post-opt instructions incl. fusion bodies): 24501 repro = 72 (6-18x win), inference_gym = 3,011 (win), jaxley = 4,434 (4.2x win), Gemma3 1B = 20,776 (runtime wash, +14% compile), TORAX ~29k. What to answer: (a) with the run-level gates active, does ANY module lose at runtime, and what is the compile-cost curve on the 5k-30k band (populate that band; it is exactly where the gate bites and the suite is thinnest); (b) build the counterexample, now above the CURRENT gate (>5,000 instructions, runtime dominated by one hot small loop, e.g. the 24501 scan embedded in ~6k instructions of medium chains): under the gate it must LOSE, quantify the loss; (c) evaluate the replacement candidates, in order: gate on thunk-level instruction count instead of total (slices and full models differ less on this metric), or replace skip-all with a per-module region-formation budget (compile cost scales with region kernels formed, not module size; degrade by keeping amplified regions first), or keep a module gate but only for the straight-line folding path (the compile-blowup class) while loop hoisting stays ungated. Calibrate whatever survives on production fold-rate telemetry, not the suite.
2. **Per-run straight-line member cap** (open question 1). The compile blowup (~N^1.8, 2.17 s at a 128-step unrolled chain) happens in SMALL modules, so no module gate can replace this. Implement the cap as a second cut criterion in the existing segmentation (see Phase B below), then calibrate the value: candidates {32, 64, 96, 128}, counting members with the internal semantics (thunk-generating instructions only). The cost of a low cap is extra per-iteration dispatch when a large amplified region splits (jaxley's largest body region is ~80 members; measure its runtime delta at each cap). The cost of a high cap is residual compile time on scalar chains. Re-run the diffrax and jax.b380442861 repros after any change here: the copy-only-region mechanism they exposed is adjacent to this logic.
3. **Kill non-amplified straight-line folding entirely** (open question 4). Every measurement of it so far is zero or negative: the frag microbenchmark was flat, Gemma3 straight-line segments were -13%, unrolled chains are the compile blowup. If the corpus confirms no straight-line once-per-call fold ever wins, apply the amplification keep-rule to unsegmented runs too, which deletes question 2's entry-side case and most of the compile-time risk class.

## Candidate unified design (evaluate; it subsumes three of the internal fixes)

The internal fixes and the shipped Gemma rule are four instances of one principle: **fold an instruction into a region only where the dispatch savings, amplified by loop trip count, exceed what its standalone thunk implementation is worth.** Instead of threading that policy through the availability predicate, the min-size counter, and the segment keep-rule separately, classify every instruction once:

- `kNever`: needs runtime services (custom-call, infeed/outfeed, collectives, sort, fft). True unavailability; a run boundary. Unchanged.
- `kAmplifiedOnly`: ops whose standalone thunk beats their in-region emission. Candidates: loop fusions protected for the new emitters (`use_experimental_loop_fusion`), copies (CopyThunk memcpy vs an in-kernel loop), fusions with `outer_dimension_partitions` set (intra-op parallelism). In amplified computations these are ordinary members. In non-amplified computations they are skipped WITHOUT breaking the run, exactly like the existing non-scalar-constant exclusion: neighbors still fold around them, and the op stays a standalone thunk, becoming a region operand or output as liveness dictates.
- `kAlways`: everything else.

Why this is better than the internal fixes it replaces: (1) the loop-fusion fix put policy into the availability check, and unavailability BREAKS RUNS, so a protected fusion mid-run fragments its neighbors' regions even in contexts where the neighbors should still fold; the skip mechanism keeps the neighbors folding. (2) The copy fix (min-size counting) stops copy-only regions but silently leaves copies inside larger non-amplified regions kernel-emitted, losing the memcpy fast path; classifying copies handles both, though the in-kernel-copy penalty needs one measurement before adopting (it may be a wash at gated sizes). (3) The policy lives in one function with one rationale, and the worthiness gate keeps its own principled form: thunk-generating member count >= 3 (the ABI break-even), or contains control flow, with >= 2 worth testing in amplified contexts.

Refinement worth one experiment, not required for v1: amplification is currently boolean, but `known_trip_count` is present in the while `backend_config` for most of these loops; a quantitative benefit model (saved thunks x trip count vs per-member penalty) would subsume the boolean and the min-size gate together. Measure whether boolean-vs-quantitative changes any corpus outcome before paying for it.

## Protocol

Phase A (corpus baseline, no code changes): for each module, interleaved D/S/D/S at `--iters` sized so a run takes 2-10 s; record compile ms, run ms, parity, region count, and classify runtime as win (>5%), wash, or loss, same for compile. Deliver the table sorted by instruction count, and separately flag which corpus entries are partial-model slices (their module-level numbers carry the caveat from question 1). The question-1 deliverable is not a module threshold: it is whether any module loses at runtime under the local gates, and what the compile-cost curve looks like on the big end, counterexample included.

Phase B (cap, code change): in `xla/service/cpu/small_region_hoisting_pass.cc`, phase 2 of `PartitionComputation`: route a run through segmentation when `run.total_bytes >= small_buffer_access_size || run.members.size() >= cap`, and add `segment.members.size() >= cap` as a flush trigger next to the byte check. The existing keep-rule (amplified or contains-control-flow) automatically turns entry-chain caps into declines. Plumb `cap` as a constructor arg with a default; strict RED-GREEN: write tests first (an entry chain of `cap+k` small ops must not fold; a while-body chain of `cap+k` ops must split into multiple calls; jaxley-shaped bodies below the cap unchanged). Then measure: unrolled_{32,128,512} compile (expect return to sentinel-level), jaxley runtime at cap in {32, 64, 96, 128} (its ~80-member regions split at the low caps; quantify), d24501 and gemma unchanged. Recommend a value.

Phase C (question 4, code change behind a bool): apply the keep-rule to unsegmented runs as well, i.e. a region folds only if amplified or contains control flow. Re-run the whole corpus. If nothing regresses beyond noise and the straight-line winners are confirmed absent, recommend adopting it and deleting the entry-side cap semantics from Phase B (the amplified-side cap stays).
